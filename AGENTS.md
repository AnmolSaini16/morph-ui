# AGENTS.md

Morph UI is a docs site for copy-paste React components built on the View Transition API and React's `<ViewTransition>`. Next.js 16 (App Router), React 19.3+, Tailwind v4, shadcn/ui.

## Commands

```bash
npm run dev       # next dev
npm run build     # next build, also type-checks
npm run lint      # oxlint
npm run format    # prettier --write .
npm test          # CSS snippet, monochrome and skill checks
npm run skill     # rebuild skills/morph-ui/ (the agent skill)
```

Always run `npm run format` and `npm run build` after changes, and `npm run skill` after changing a component, an example, `morph.css`, the entries or `src/lib/reference.ts`. Verify visible behavior in a real browser; don't ask the user to check.

## Registry components

These are the product. Rules:

- **React's `<ViewTransition>` only.** Never call `document.startViewTransition()`; it interrupts React's transitions. Changes animate only inside `startTransition` (or Suspense / `useDeferredValue`); a plain `setState` doesn't.
- **Reusable API.** Data comes in through props. Sample data and demo controls live in `src/components/docs/examples/`, not in the component.
- **Self-contained.** Plain HTML elements and Tailwind classes only. No imports from `@/components/ui` or `@/lib`, no `cn()`. The only import is `react`. Icons are small inline SVGs of our own (16px grid, 1.5 stroke, `currentColor`), defined at the top of the file; demos use the same style. Never add an icon package.
- **Use the user's theme, ship no colors.** Only shadcn's color names (`bg-card`, `text-muted-foreground`, `ring-ring`, `border-border`), so installed code themes itself; each page lists the variables it reads. Give every border a color class, and set a text color on the outer wrapper (`text-foreground` or `text-card-foreground`) instead of inheriting it from `body`.
- **Start with `"use client"`.** Formatting is Prettier's (no semicolons, 100 columns): run `npm run format`. Keep comments rare: only where the code can't say why.
- **Compose the `vt-*` classes in `morph.css`.** No component-specific CSS: a component combines existing classes (`update="vt-move vt-shell"`). Add a new class only for a pattern that could serve other components, name it generically, and document it in the class list on the Getting started page. Class names are public API; don't rename them. Tailwind can't style `::view-transition-*` pseudo-elements (they live on the root, not the element), so this CSS can't move into class strings. Anything outside a transition (e.g. a header fading in) uses Tailwind: `transition-opacity starting:opacity-0`.
- **Buttons are real `<button type="button">`** with `cursor-pointer` in the class string.
- **Keep controls outside animated boundaries.** Elements inside a `<ViewTransition>` can't be clicked while it animates. Headers, back buttons and remove buttons sit outside, and use a plain CSS entrance animation if they need one (`transition-opacity starting:opacity-0`, see the Stack Navigator header).
- **Never make a click wait.** React holds a new transition until the running view transition ends, so a click mid-animation feels dead. Call `document.activeViewTransition?.skipTransition()` right before every `startTransition` (in components and in the example code) to finish the running one instantly.
- **Guard no-op clicks.** A tab or dot that's already active must not start a transition.
- **No motion on keyboard input.** Arrow keys and shortcuts set state directly (after `skipTransition()`), never through `startTransition`. See Tabs and Carousel.
- **Motion budget.** UI motion stays under 300ms; frequent UI (tabs, toggles) uses `vt-quick` (~210ms). Only spatial morphs (a card opening, the island) take `--vt-move`/`--vt-slow`. Never `ease-in`; fades use `--vt-ease-out`, moves `--vt-ease`. Nothing scales from below 0.9.
- **Fixed heights** around anything that grows or shrinks, so the page never shifts.
- **Responsive by container.** Use container queries (`@container`, `@md:`) so a component fits whatever space it gets.
- **Move focus** into newly opened content, and back to the trigger on close.

### ViewTransition patterns

- Classes, not names, drive the CSS: `update="vt-move vt-shell"` → `::view-transition-group(.vt-shell)`. Snapshots can't read CSS variables set on the component (they hang off the root); users tune through `:root { --vt-*: … }`.
- Direction the user chose (next/back, push/pop): `addTransitionType("stack-push")` inside `startTransition`, mapped with `update={{ "stack-push": "vt-push vt-clip vt-forward", default: "none" }}`.
- Direction derived from data (a number going up): `vt-forward` / `vt-back` from state.
- Shared elements: `name` + `share`. Namespace names with `useId()` so two instances never pair. Both sides of a pair must be nested the same way; a top-level boundary won't pair with a nested one (Post List wraps the article in an inert `<ViewTransition default="none">` for this reason).
- `enter`/`exit` only fire on the outermost `<ViewTransition>` of an inserted or removed subtree, and it must wrap a DOM element directly.
- Use functional state updates: while a view transition runs, React holds later transitions, so closures go stale.

### CSS gotchas

- Snapshots paint above the page and ignore ancestors' `overflow`. Clip with `overflow: clip` plus `border-radius` on `::view-transition-image-pair`, or a `clip-path` inside the keyframes.
- A keyframe with `clip-path` must list both ends; it can't interpolate to `none`.
- Surfaces using `vt-shell` or `vt-expand` get a 1px ring painted on the group while they animate (`--vt-ring`). Style the element with the same `ring-1 ring-foreground/10`, never a `border`, and drop it only while it animates with `[&[style*=view-transition-name]]:ring-0` (React sets that inline name on an element just for its own transition). Otherwise the snapshots carry their own outline, which shows as a second, smaller outline inside the resizing surface (most visible when it shrinks). Never put `transition-shadow` (or any transition covering `box-shadow`) on such a surface: when the transition ends the ring comes back through that transition, so the outline blinks out and fades in.
- `box-shadow` rings sit outside the box and get clipped or doubled in snapshots. Use a real `border` on anything that slides, or paint the surface on `::view-transition-group` and hide or pin the old/new images.
- `animation-direction: reverse` also reverses the easing. For exits that need their own easing, write explicit keyframes (see `vt-push-*`).
- Reference every `@keyframes` from an `animation` shorthand, never only `animation-name`. If CSS is ever merged into a Tailwind file (the shadcn CLI's `css` field puts keyframes inside `@theme`), Tailwind drops keyframes it doesn't see used.
- Never use `:root:active-view-transition` to hide or restyle something: it matches any transition on the page, so a click in another component makes it flicker. Scope it to the component: `[&[style*=view-transition-name]]:` on the animating element, or `group-has-[[style*=view-transition-name]]/name:` on a live control whose component is animating.
- Crossfades pair old and new in one image pair and blend with `plus-lighter` (same duration and curve, one out, one in). Only `:only-child` may follow `::view-transition-old/new`; `:not(...)` there silently drops the whole rule.
- Moving content (slides, rolls) animates only `translate` and `opacity`, never `filter`: blur on moving text makes it soft and costs frames on phones. Blur stays only on crossfades, where it's cosmetic.
- WebKit (Safari, every iOS browser) draws `filter: blur()` snapshots offset and jumps when the transition ends. That's a rendering bug with no feature to detect, so `morph.css` turns the blur off there with `@supports (font: -apple-system-body)`. Everything else is feature-detected: without nested groups (`@supports not (view-transition-group: contain)`, Safari today), children can't be clipped by their parent's group, so a `vt-fade` element leaving on its own is dropped at once instead of fading outside its card. Never sniff the user agent.
- Keep text layout identical on both sides of a transition where you can (e.g. a stats row that stays on one line): the browser crossfades two text layouts; it can't reflow letters between them.
- Reduced motion is gentler, not off: groups jump, old/new still crossfade over 150ms. Don't set durations to 0 in new CSS.
- Only use selectors Lightning CSS knows (Next.js and Tailwind parse with it). Newer pseudo-elements like `::view-transition-group-children` become a warning in every user's dev console; a test parses `morph.css` and every snippet to catch this.
- Settings are never declared: write `var(--vt-move, 420ms)` with the default from the list at the top of `morph.css`, every time. Only `view-transition-name: none` goes on `:root`. A test checks every setting has one consistent default. Reuse existing settings (`--vt-exit`, `--vt-enter`, `--vt-move`, `--vt-ease`) instead of new durations.

## Docs site

- `:root { view-transition-name: none }` (in `morph.css`): the page itself is never captured, so only boundaries animate and the rest stays clickable.
- Page changes blur through `PageTransition` (`src/components/docs/page-transition.tsx`), rendered in the docs shell around the page. It's a `<ViewTransition>` keyed by `usePathname()`, so every route change at any depth swaps the page, with one `name` and `share="vt-blur"` so the old and new page pair into a single crossfade (a separate exit and enter would overlap without `plus-lighter` and dip). Don't use `app/template.tsx` for this; a template only re-mounts when its own segment changes, so nested routes wouldn't animate.
- `DocsLink` in `src/components/docs/navigation.tsx` only moves the sidebar highlight instantly.
- Theme: `next-themes` in `src/components/theme-provider.tsx`, plus a D-key shortcut.
- The site is a static export (`output: "export"`) deployed to Cloudflare Workers static assets (`wrangler.jsonc`, `public/_headers`). Nothing may need a server: metadata routes (OG images, sitemap, robots) export `dynamic = "force-static"`, and extensionless image routes get their `Content-Type` from `public/_headers`. Absolute URLs come from `NEXT_PUBLIC_SITE_URL` (set in `.env.production`), read in `src/lib/site.ts`.
- Installation is manual: copy Component, its generated CSS, and Usage from one page. The full `morph.css` is optional for multi-component installs. `src/lib/component-css.ts` declares style dependencies and generates snippets from the canonical stylesheet. No shadcn registry yet.
- The shadcn CLI sometimes adds a bogus `cn` package and `from "cn"` imports when adding UI components; rewrite them to `@/lib/utils` and uninstall it.

## Adding a component

1. `src/registry/<slug>.tsx`, built from the existing `vt-*` classes. Only add to `morph.css` if a new, reusable pattern is needed.
2. Add a demo at `src/components/docs/examples/<slug>.tsx` and register it in `src/components/docs/demos.tsx`.
3. Add the entry to `src/lib/entries.ts`, its CSS dependencies to `src/lib/component-css.ts`, and an explanation to the component page.
4. Run `npm run skill` so the agent skill includes it. A new `vt-*` class also goes in `classGroups` in `src/lib/reference.ts`; a test fails if one is missing.

## Skill

`skills/morph-ui/` follows the Agent Skills format (`SKILL.md` with `name` and `description` frontmatter, plus `references/` and `assets/`), so `npx skills add <owner>/<repo>` finds it. It's generated:

- Prose: `scripts/skill/SKILL.md` and `scripts/skill/patterns.md`, with `{{placeholders}}` the build fills in. Prettier ignores these templates and the output, because it misreads the placeholders inside code fences.
- Everything else comes from the site's sources: component and example files (examples rewritten to import from `@/components/`), `morph.css`, `entries`, `componentClasses`, `classGroups` and the settings table at the top of `morph.css`.
- `tests/skill.test.mjs` fails if the folder is stale, the frontmatter is invalid, a code fence is unbalanced, or a class in `morph.css` is undocumented.
- `skills/` is excluded from `tsconfig.json`: its examples import `@/components/…`, which only exists once installed.
- Keep the skill's rules in step with the "Registry components" rules above; they're the same rules, written for someone using the components.
